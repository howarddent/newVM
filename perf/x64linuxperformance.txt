newVM Performance Benchmark
============================
MatMult / LinearSolve / Invert, N = 10 / 100 / 1000, all four TVMobj* types
Library-backed (MKL + IPP + OpenBLAS) vs PUREPASCAL, Linux/x86_64

Machine: Intel(R) Core(TM) i7-14650HX, 24 logical CPUs, 31 GiB RAM
OS: Linux 7.0.0-28-generic (Ubuntu 24.04)
Backends detected by ./newvmconfigure: MKL (libmkl_rt), IPP
(ippcore+ippvm+ipps), OpenBLAS, FFTW3 (double+single) - all found, so the
"real" build for this machine is fully library-backed (PUREPASCAL and
PUREPASCAL_BLAS both inactive). The PUREPASCAL comparison column below
was produced from a second build with newVMConfig.inc hand-forced to
{$DEFINE PUREPASCAL}/{$DEFINE PUREPASCAL_BLAS}, same technique as
perf/OSXperformance.txt, then regenerated back to the real per-machine
config via ./newvmconfigure afterwards.

Plain text rather than RTF here (unlike perf/OSXperformance.txt, which
used RTF verified via macOS's textutil) - no equivalent tool assumed
present on this machine, and plain text is sufficient.

Test suite: ./newVMtest (full 256-test FPCUnit suite, all five TVMobj*/
TVMobjI types) - 256 run, 0 errors, 0 failures, against the real
(library-backed) build.

NOTE on LinearSolveZ/LinearSolveC: newVMbench.lpr's banner text
unconditionally prints "PUREPASCAL always ... identical in both builds"
for these two operations. That claim is only true on a machine where
PUREPASCAL is already forced on for the "real" build too (e.g. the Mac
in perf/OSXperformance.txt, which has no MKL/IPP). On THIS machine the
real build has PUREPASCAL undefined, so LinearSolveZ/LinearSolveC's own
{$IFDEF PUREPASCAL} branch (see newVMComplex.pas/newVMComplexSingle.pas)
genuinely takes the library-backed lapacke_zgesv/zgetrs (resp. cgesv/
cgetrs) path there, NOT PurePascalLUZ/LUC - the banner text is simply
wrong for this platform. The timings below confirm this: LinearSolveZ/C
differ substantially between the two builds here, unlike on the Mac.
Not fixed in newVMbench.lpr as part of this run - flagged here so the
numbers aren't misread against the printed (misleading) banner.

All timings in milliseconds, single run per row (not averaged). Residuals
are Frobenius-norm ||A*x-b|| (solve) / ||A*Ainv-I|| (invert); both builds
compute the same correct answer to within precision-appropriate tolerance.
Speedup = PUREPASCAL time / library-backed time. N=10 timings are at or
below timer resolution for several operations - "~parity" means the two
numbers are both sub-0.05ms noise, not a meaningful comparison.

Summary: as expected, the gap between library-backed and PUREPASCAL grows
sharply with N (all three operations are O(N^3)). MatMult sees the
largest speedups (278x-758x at N=1000, MKL/OpenBLAS's cblas_?gemm vs a
plain triple loop). LinearSolve sees the smallest (6x-43x at N=1000) -
PurePascalLU?/LU?Solve is a reasonably competitive single-threaded partial-
pivoting LU, whereas MatMult's naive triple loop has no cache blocking or
vectorisation at all. Invert lands in between (24x-516x), tracking
LinearSolve's LU cost plus an extra O(N^3) triangular-solve pass for the
inverse. Residuals confirm both variants compute the same correct answer
at each N and precision (double ~1e-15 to 1e-11, single ~1e-6 to ~5e-2 at
N=1000, i.e. still within expected single-precision O(N) error growth).
